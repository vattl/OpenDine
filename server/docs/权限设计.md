# 点餐系统权限设计

> **连锁模式补充**：多店下的**数据范围**（总部 / 区域 / 门店）与门店独立 **`code`**、运营前端状态与请求头约定，见 **`docs/admin_chain_permission_architecture.md`**。本文 **§2～§5** 侧重 **业务权限码（RBAC）**；与连锁范围组合时，服务端宜 **先校验数据范围，再校验权限码**。

## 1. 概述

- **C 端（小程序）**：`POST /order/getOpenid` 用一次性微信 `code` 换取 `openid` 与服务端签发的 `user_token`；用户私有数据与写接口必须携带 `X-User-Token`，后端校验请求内所有 `openid` 与 Token 身份一致。菜单、门店配置等显式公开接口无需该 Token。
- **B 端（运营后台）**：采用 **RBAC（角色-权限）** 模型，管理员登录后获得 JWT，访问 `/admin/*` 接口时除校验登录外，按**权限码**控制各模块功能是否可用。

> C 端 `openid` 只能作为数据键，不能作为身份凭证；控制器不得通过手机号、`user_id`、订单号或排队号绕过 `X-User-Token` 所绑定的身份。

> 兼容性说明：少量历史管理接口仍位于 `/order/*`、`/activity/*`，但已显式纳入 B 端拦截器；路径前缀看似公开不代表匿名可写，权限以服务端方法+路径映射为准。

## 3. 数据库设计与权限获取逻辑

### 3.1 表结构（与 db_diancan_permission.sql 一致）

| 表名 | 说明 | 关键字段 |
|------|------|----------|
| t_role | 角色 | id, role_code, role_name |
| t_permission | 权限 | id, permission_code, permission_name, module |
| t_admin_role | 管理员-角色（多对多） | admin_id → t_admin.id, role_id → t_role.id |
| t_role_permission | 角色-权限（多对多） | role_id → t_role.id, permission_id → t_permission.id |
| t_api_permission | 接口-权限映射（可选） | method, path_pattern, permission_code |

- 现有 **t_admin** 不变，通过 **t_admin_role** 关联角色。执行脚本后需为管理员绑定角色：  
  `INSERT INTO t_admin_role (admin_id, role_id) SELECT id, 1 FROM t_admin;`（1 为 super_admin）。

### 3.2 权限获取逻辑（与后端 AdminPermissionServiceImpl 一致）

1. **入参**：管理员 ID（`t_admin.id`）。
2. **步骤 1**：查 **t_admin_role**，`WHERE admin_id = ?`，得到该管理员的 **role_id 列表**。
3. **步骤 2**：若 role_id 列表为空（未分配角色），返回空权限集合；只有显式绑定 `super_admin` 角色并通过角色权限表配置，才能获得总部权限。
4. **步骤 3**：若 role_id 列表非空，用 **t_role_permission** 关联 **t_permission**，`WHERE rp.role_id IN (roleIds)`，得到去重后的 **permission_code** 列表（多角色为并集）。
5. **步骤 4**：返回 `Set<String>` 权限码，供登录响应与拦截器校验使用。  
- 若权限表未创建或查询异常，后端返回空权限集合并拒绝请求（失败关闭）。

## 4. 接口与权限映射（B 端）

以下为运营后台接口与所需权限码，用于实现时在拦截器或注解中校验。

> **运行时单一权威（WI-062-AUTH）**：`t_api_permission` 是 B 端接口入口权限映射的唯一运行时权威。`SysInterceptor` 未命中数据库映射时一律失败关闭，不再回退代码内置清单。`ApiPermissionMapping` 仅用于审计清单、V041/初始化 SQL 生成与启动漂移告警；它不能授权请求。数据库加载异常时保留最后一次成功快照，首次加载失败则受保护接口失败关闭。

> **敏感动作三态**：`cashier:operate` 只表示收银入口和发起审批资格，不表示退款、改价、优惠或反结账执行权。统一决策器输出 `ALLOW / REQUIRE_APPROVAL / DENY`；精确执行权限分别为 `order:operate:refund`、`order:operate:changePrice`、`order:operate:discount`、`order:operate:reopen`，审批权限为对应的 `:approve`。

> **WI-063 角色迁移**：V042 从内置 `cashier` 角色撤销上述四个 execute 及四个 approve 权限，只保留 `cashier:operate`；`boss`、`store_manager`、超级管理员及历史管理角色显式获得精确 execute/approve。自定义角色不做泛化回填，必须按岗位逐项授权，拥有退款权限不会连带获得改价、优惠或反结账。

## 5. 鉴权流程（B 端）（后端拦截器严格按此实现）

1. **请求头**：请求携带 `Authorization: Bearer <JWT>`（或 `Authorization: <JWT>`，拦截器会去掉 Bearer 前缀）。
2. **步骤 2**：拦截器校验 JWT 有效且 subject 为管理员身份；若未登录或非法 token，直接返回 **401**，响应 body：`{ "code": 401, "msg": "未登录或登录已过期" }`。
3. **步骤 3**：从 JWT 的 id 解析出管理员 ID，再根据 **t_admin_role → t_role_permission → t_permission** 得到权限集合。
4. **步骤 4**：根据请求路径 + 方法查 **接口-权限映射**，得到所需权限码。
5. **步骤 5**：若当前管理员拥有该权限码（或为 super_admin 角色，拥有全部权限），放行；否则返回 **403**，响应 body：`{ "code": 403, "msg": "无权限：<权限码>" }`。
6. **门店上下文（连锁，2026-04）**：在 JWT 与权限码校验通过之后，对 **`/admin/**`**（白名单前缀除外）与 **全部 `/cashier/**`**，`SysInterceptor` 还要求请求能解析出**营业中**的当前门店（`X-Shop-Id` / `X-Shop-Code` 或与 `ShopChainSupport` 一致的 body/query 字段）；缺失或无效时返回 **4001**（业务体 `code` 与 `msg` 以后端为准）。解析成功的门店 ID 写入请求属性，业务代码通过 **`AdminShopRequest.getResolvedShopId`** 读取；**不得以**前端单独传来的 `shop_id` 作为唯一数据范围依据（报表、日结、订单列表等均以解析结果为准，防串店）。跨店操作资源时返回 **4003**。白名单路径与模块级行为见 **`docs/backend_chain_store_api.md` §3.3、§7.6**；库表迁移见 **`docs/db_migration_material_payment_log_shop_id.sql`**（原料、支付方式、操作日志等 `shop_id` 列）。
7. **安全审计**：后台 401/403/4003、C 端身份归属拒绝、KDS 设备鉴权失败，以及角色、权限、接口映射、管理员角色和数据范围变更统一写入 `t_operation_log`（`module=security`）。日志只记录身份 ID、方法、路径、权限码、门店和 traceId，不记录密码、token、openid 等敏感值；日志写入异常不得改变鉴权结论。

## 5.1 前端如何登录并获取权限内容（后端严格按此实现）

### 登录

- **请求**：`POST /adminLogin`，Content-Type: application/json。  
  **请求体**：`{ "userName": "xxx", "password": "xxx" }`。
- **成功响应**（HTTP 200）：  
  `{ "code": 0, "token": "<JWT>", "permissions": ["order:view", "dish:manage", ...], "adminId": 1, "userName": "admin", "scope": "HQ"|"REGION"|"SHOP", "shops": [{"id":1,"code":"SH001","name":"总店"}], "regionIds": [1,2] }`  
  - `code`: 0 表示成功。  
  - `token`: JWT，后续请求均需携带。  
  - `permissions`: 权限码数组，用于菜单/路由/按钮显隐（如含 `order:view` 才展示订单管理）。  
  - `adminId`、`userName`: 当前管理员 ID 与用户名。  
  - `scope`：**连锁数据范围**——`HQ` 表示总部/超管语义（可管营业中全部门店）；`REGION` 表示按 `t_admin_region` 解析区域门店；`SHOP` 表示仅 **`t_admin_shop`** 绑定门店。若同时有区域与门店绑定，按实现取交集。  
  - `shops`: 当前账号可选门店列表（`id`、`code`、`name`），供顶栏选店；运营请求需门店上下文时配合 **`X-Shop-Id`** 或 **`X-Shop-Code`**。  
  - `regionIds`: 当前管理员可访问区域 ID 列表（`scope=REGION` 常用，HQ/SHOP 可为空）。  
- **失败响应**（如用户名或密码错误）：`{ "code": 500, "msg": "用户名或者密码错误！" }`。  
- **前端约定**：持久化 `token`（localStorage/sessionStorage），将 `permissions` 与 **`scope`/`shops`** 存入内存或 store；需门店的 B 端请求附带 **`X-Shop-Id`** 或 **`X-Shop-Code`**。

### 刷新页面后恢复权限

- **请求**：`GET /admin/me/permissions`，请求头 `Authorization: Bearer <token>`。
- **成功响应**：`{ "code": 0, "permissions": ["order:view", ...], "adminId": 1, "scope": "HQ"|"REGION"|"SHOP", "shops": [...], "regionIds": [1,2] }`（字段与登录成功响应一致，无 `token`）。  
  前端用返回的 `permissions` 与 **`scope`/`shops`** 更新 store/状态即可。

### 可访问门店分页（大门店量）

- **请求**：`GET /admin/me/shops?page=1&pageSize=20&keyword=`，请求头 `Authorization: Bearer <token>`。
- **成功响应**：`{ "code": 0, "scope": "HQ|REGION|SHOP", "regionIds": [1,2], "list": [{"id":1,"code":"SH001","name":"总店"}], "page":1, "pageSize":20, "total":100 }`。
- **用途**：HQ 门店量大时，前端不依赖登录一次性全量 `shops`，改为分页懒加载选店列表。
- **未登录或 token 无效**：`{ "code": 401, "msg": "未登录或登录已过期" }`，前端应跳转登录。

### 后续请求

- 所有 B 端接口（除 `POST /adminLogin`）均需在请求头携带 `Authorization: Bearer <token>`。
- 需要门店上下文的模块（订单、报表、日结、桌台、菜品、类目、优惠券、会员消费/画像、原料、支付方式、日志等）须在封装层**自动附加 `X-Shop-Id` 或 `X-Shop-Code`**（与顶栏当前选中门店一致），与 **`docs/backend_chain_store_api.md` §7.6**、**`docs/openapi.yaml`** 中 **`components.parameters.XShopId`** 说明一致。
- **401**：`{ "code": 401, "msg": "..." }`，前端跳转登录。  
- **403**：`{ "code": 403, "msg": "无权限：xxx" }`，前端提示无权限。
- **4001 / 4003**：缺少门店或资源不属于当前店时，提示用户检查是否已选店或切换门店。

## 6. C 端与特殊接口说明

- **C 端**（如 `/order/*`、`/dish/*`、`/coupon/*` 等）：不参与上述权限体系，仍以 openid/业务参数校验；若部分接口（如 `/order/delete`）供后台调用，可在后台前端仅对具备相应权限的角色展示入口，后端可保留现有鉴权或增加 B 端 token 校验。
- **支付回调**（如 `/order/pay/notify`）：无需 JWT，由微信签名等单独校验。
- **对外打印接口**（如 `/order/autoAcceptAndPrint`、`/order/printContent`）：若仅内网或第三方调用，可通过 IP/密钥等方式控制；若需纳入权限，可单独增加权限码（如 `order:print`）并在文档中注明。

## 7. OpenAPI 文档约定

- 在 **components.securitySchemes** 中定义 `BearerAuth`（JWT）。
- 所有 B 端接口在文档中注明 **security: BearerAuth**，并在 **description** 或 **x-permission** 中写出所需权限码，便于前端按权限控制菜单与按钮，后端按同一权限码做校验。
