# 餐饮收银 SaaS 与 AI 经营参谋平台

> **产品需求文档（PRD）｜V1.0｜2026-10-08｜状态：产品方案 / 待研发评审**  
> **产品定位：免费完成日常经营，付费获得深入分析与经营决策建议。**  
> 适用对象：产品负责人、前后端研发、测试、设计、运营与商业化团队。

---

## 0. 执行摘要与决策清单

**一句话方案：** 在已有自研餐饮收银系统上增加 SaaS 多租户、套餐订阅、统一经营数据平台和 AI 经营参谋。商家既可使用系统自身的订单数据，也可导入第三方收银系统数据；正常点餐与收银长期可用，历史经营分析和 AI 决策能力按订阅收费。

**本版确定的产品原则**

1. **核心营业功能不锁定。** 免费版保留商品、桌台、扫码点餐、收银结账、基础 KDS、订单查询、退款/售后、基础对账与必要导出；付费到期不能导致门店停业。
2. **「当日数据免费」限定为经营概览。** 按营业日展示当日营业额、订单数、商品销量；历史订单明细继续允许查询，历史趋势、利润分析及跨期诊断为增值功能。
3. **自有 POS 与第三方数据走同一分析引擎。** 数据来源要可追溯、口径要一致，不以来源决定分析结论。
4. **确定性计算优先。** 金额、利润、同比/环比等先由指标引擎计算；AI 只承担异常解释、因果假设、策略建议和可读报告。
5. **默认只读、商家掌控。** AI 不自动改价、退款、采购、发券、发送营销消息或操作收银；未来执行类操作须另行设计授权确认。
6. **先单店、小微商家，再多门店与复杂集成。** 不为初期商业化重构整个 POS；优先验证 10 家真实付费商家。

**立项前待确认（不阻碍 PRD 评审）**

| 编号 | 决策项 | 本版默认方案 | 验证方式 |
|---|---|---|---|
| D-01 | 收费主体 | 按门店/月收费；一个商户可管理多门店 | 运营访谈与定价实验 |
| D-02 | 支付路径 | 初期按月主动续费，不默认自动扣费 | 支付能力评估 |
| D-03 | 目标客群 | 1～3 家门店的小型餐饮；烧烤/小吃/快餐优先 | 首批试点 |
| D-04 | 既有系统接口 | 复用已有 POS/KDS/WebMCP 能力，实际接口与权限以现有 OpenAPI 为准 | 技术盘点 |
| D-05 | 外部导入方式 | V1.1 先 Excel/CSV，官方授权 API 放在后续 | 样本报表验证 |
| D-06 | 价格 | 免费 / 专业 59 元 / AI 经营 149 元；独立分析 99 元，均为待测试价 | 付费意愿测试 |

## 1. 项目背景

### 1.1 现状与机会

项目已有自研餐饮收银相关能力，包括扫码下单、商品与订单、结账、出餐/KDS，以及围绕经营数据的只读 WebMCP 探索。现阶段系统主要用于自身门店运营，尚不能直接等同于可对外商业化的多租户 SaaS；账户隔离、套餐、订阅、账单、数据安全、客服与运维能力需要补齐。

餐饮商家通常已拥有收银工具，但仍会遇到「知道今天卖了多少，却不知道为什么赚得少、哪里效率低、接下来怎么改」的问题。项目利用真实餐饮业务经验，把免费工具转化为持续使用入口，并以能够解释问题、形成可执行策略的 AI 经营参谋创造订阅价值。

### 1.2 产品愿景

**让小餐饮老板无需更换收银系统，也能获得可信、可执行、可追踪的经营建议。**

### 1.3 产品边界

**纳入：** 自有 POS 数据读取、商户/门店/成员、套餐和会员、基础统计、历史分析、手动文件导入、数据标准化、AI 诊断、日报周报、订阅支付、审计日志、后台运营。

**暂不纳入首发：** 完整供应链 ERP、跨品牌自动爬取收银数据、自动改价/采购/退款、AI 自动营销发送、复杂连锁总部核算、财税申报、实时机器学习预测、替换商家现有支付通道。

## 2. 目标用户与典型任务

| 角色 | 典型痛点 | 核心任务 | 权限重点 |
|---|---|---|---|
| 单店老板 / 商户所有者 | 没时间每天看复杂报表，不知道问题根源 | 看当日概览、支付订阅、查看 AI 建议 | 本商户全部门店与账单 |
| 店长 | 高峰出餐慢、排班备货凭经验 | 查看本店趋势与异常、执行改善 | 本店经营分析，不见其他店 |
| 收银员 / 服务员 | 只想稳定下单收款 | 点餐、结账、查单、必要退款 | 按岗位授权，不见 AI 财务或账单 |
| 财务 / 运营 | 口径不统一、报表难对账 | 查询明细、分析成本、核对来源 | 指定报表及导出权限 |
| 第三方收银商家 | 不愿替换现有收银系统 | 注册→上传报表→获得诊断 | 仅管理授权导入的数据 |
| 平台运营 | 需要了解增长和服务异常 | 配置套餐、处理订单、排查导入 | 最小权限、全程审计 |

### 2.1 核心场景

- **场景 A｜免费收银商家：** 新用户完成注册和门店创建，录入商品、打印设备设置后开始正常点餐与收银，每天看到基础营业数据。
- **场景 B｜升级专业版：** 老板想查看最近 90 天商品销售排行、时间段营业趋势、成本与毛利（前提是成本数据完整），通过会员页面购买并立即开通。
- **场景 C｜升级 AI 经营版：** 系统发现有证据支撑的异常，展示免费摘要；老板解锁完整诊断、改进建议和一周后的效果追踪。
- **场景 D｜第三方收银独立用户：** 商家下载原系统 Excel/CSV，上传并确认字段映射、数据时间段和缺失项，得到分析报告；无需迁移收银系统。
- **场景 E｜会员到期：** 高级分析停止新增，历史已购报告按约定期限可查看；收银、订单、售后和基本数据访问不受影响。

## 3. 商业模式与版本策略

### 3.1 版本与建议试运行价格

> 下表为**价格假设**，用于灰度测试，不构成最终定价承诺。首期仅支持单店套餐；多门店按门店分别授权，统一商户支付能力后续建设。

| 能力 | 免费版 0 元 | 专业版 59 元/月 | AI 经营版 149 元/月 | 独立 AI 分析版 99 元/月 |
|---|---|---|---|---|
| 收银/点餐/基础 KDS | 可用 | 可用 | 可用 | 不提供 POS |
| 当日营业概览 | 可用 | 可用 | 可用 | 取决于导入数据 |
| 历史订单明细/售后查询 | 可用 | 可用 | 可用 | 仅授权导入范围 |
| 历史趋势和商品分析 | 不含 | 包含 | 包含 | 包含 |
| 成本/毛利分析 | 不含 | 数据齐备时可用 | 数据齐备时可用 | 数据齐备时可用 |
| AI 诊断及改善建议 | 限定摘要预览 | 不含 | 包含 | 包含 |
| 自动日报/周报 | 不含 | 不含 | 包含 | 导入数据更新后生成 |
| AI 自然语言问数 | 不含 | 不含 | 有额度 | 有较低额度 |
| 第三方 CSV/Excel | 不含 | 可加购/后续开通 | 包含 | 包含 |
| 官方第三方 API 同步 | 不含 | 暂不支持 | 后续可加购 | 后续可加购 |

**套餐计量规则：** 以 `store_id + subscription_period` 为功能归属；AI 请求量、导入次数、文件大小可配置额度；套餐限额在服务端执行。精确配额初期由成本试点确定，避免以「无限使用」承诺产生亏损。

### 3.2 免费策略与付费边界

- **永不因未付费拦截：** 点餐、收款、已授权退款、商品修改、订单记录与查询、当日概览、依法/依合同必要的数据导出。
- **免费历史明细 ≠ 免费历史分析：** 明细服务于对账与售后，趋势聚合、分布归因、跨期比较和 AI 建议才是付费点。
- **免费诊断预览：** 仅在指标满足数据门槛、确有异常证据时出现；不得伪造异常或使用恐吓式文案。
- **到期处理：** 新高级查询不可执行；已生成报告按合同与数据保留政策继续查看/导出；下单与收银永不受影响。
- **对外承诺：** 不保证「盈利提升 X%」或任何确定收益结果。

### 3.3 转化与留存闭环

获客入口（内容/搜索/转介绍）→ 免费注册或导入体验 → 得到真实数据价值 → 看到完整分析能力预览 → 自主订阅 → 自动开通 → 定期报告与改善追踪 → 主动续费/合规自动续费。

首次付费只通过经营价值触发，不通过强制中断营业触发。

## 6. 模块需求：商户、门店与权限

### 6.1 商户与门店模型

- **FR-001｜商户注册 [V1.0]：** 手机号等合规方式注册；支持登录、找回、注销申请；商户创建时生成不可变 `tenant_id`。
- **FR-002｜门店建档 [V1.0]：** `store_id` 归属唯一商户；配置名称、行业、时区、营业日截止时间、收银设置；默认 `Asia/Shanghai` 和凌晨 **06:00** 截止，允许合法范围内调整。
- **FR-003｜成员和角色 [V1.0]：** 所有者、店长、收银员、财务/分析员、自定义角色；权限按「商户/门店/操作/字段」控制。
- **FR-004｜租户隔离 [V1.0]：** 用户查询、导出、后台任务、AI 调用均必须经服务端强制核验 `tenant_id`、`store_id` 与授权范围；不能信任前端传入的门店 ID。
- **FR-005｜多门店准备 [V1.0]：** 数据模型预留多门店和门店切换；跨门店聚合、统一计费及连锁报表暂不开放。

**验收：** 店长不能访问未授权门店；收银员不能读毛利和账单；修改请求参数不能越权导出订单；授权变更在后续请求生效。

### 6.2 经营时间口径

- **FR-006｜营业日 [V1.0]：** 2026-10-08 02:00 的订单，在门店设定 06:00 截止时归属 2026-10-07 营业日；报表须同时保留真实时间戳和营业日标签。
- 调整截止时间不直接覆写历史结果；按新旧规则标记生效时间，重算历史须管理员确认并生成审计记录。
- 店铺时区用 IANA 时区标识存储，避免跨地区、多门店和夏令时问题。

## 7. 模块需求：免费收银与基础概览

- **FR-010｜免费核心收银 [V1.0]：** 沿用现有 POS 能力提供商品/桌台/扫码点餐/收款/订单状态/基础 KDS；不为收费重写订单核心链路。
- **FR-011｜当日概览 [V1.0]：** 展示当前营业日实收、有效订单数、客单价、畅销商品、支付方式拆分；各指标附「统计时间与口径」入口。
- **FR-012｜历史明细 [V1.0]：** 允许按日期、订单号、支付状态查单；支持投诉与对账所需的合理查询/导出；不提供免费跨期趋势图和高级归因。
- **FR-013｜离线/网络异常 [V1.0]：** 复用现有 POS 的容错机制；当 AI、报表、订阅或导入服务不可用时，核心订单与支付链路必须独立运作。若现有 POS 不具备离线能力，不在本次改造中虚假承诺。
- **FR-014｜免费版提示 [V1.0]：** 高级功能页说明用途、样例、价格与数据前提；不打断收银员操作，不使用全屏强制弹窗。

**边界案例：** 跨午夜营业、部分退款、整单作废、优惠券、组合套餐、现金/微信混合支付、延迟支付通知、跨天补单。

## 8. 模块需求：SaaS 套餐、订阅与支付

### 8.1 权益模型

- **FR-020｜服务端权益中心 [V1.0]：** 基于 `plan_code / feature_key / quota / effective_at / expires_at` 配置套餐。初始功能键建议：
  - `analytics.history.view`、`analytics.product.view`、`analytics.cost.view`
  - `data.import.csv`、`ai.diagnosis.run`、`ai.report.daily`、`ai.report.weekly`
  - `ai.chat.use`、`billing.manage`、`data.export.basic`
- **FR-021｜授权维度 [V1.0]：** 权益受「商户付费身份 + 门店是否被授权 + 员工 RBAC」三重约束；拥有会员不意味着所有员工可看财务数据。
- **FR-022｜免费保障 [V1.0]：** `pos.order.create`、`pos.checkout`、`pos.order.history.basic` 等经营基础权限不能与会员到期状态耦合。

### 8.2 支付与账单生命周期

- **FR-023｜订单支付 [V1.0]：** 展示套餐、计费周期、到期时间、费用、退款说明；商家主动确认支付；异步回调验签并按支付平台订单号+内部订单号幂等入账；回调顺序错乱需可恢复。
- **FR-024｜订阅状态机 [V1.0]：** `FREE → ACTIVE → EXPIRED`；支持 `PENDING_PAYMENT、CANCELED、REFUNDING、REFUNDED`。`TRIAL、PAST_DUE` 作为后续可配置状态，不假设自动续费已开通。
- **FR-025｜升级与续费 [V1.0]：** 付费成功立即生效；同套餐续费顺延原到期日（若已过期，从支付成功时间起计）；不同套餐中途升级按明确展示的金额与生效策略处理，首期可只允许到期切换以简化财务。
- **FR-026｜到期降级 [V1.0]：** 只关闭高级新分析请求，保留 POS；管理员可查看有效账单、已购服务记录；停用 AI 自动任务并及时释放资源。
- **FR-027｜退款与争议 [V1.0]：** 用户有退款/取消入口或工单路径；退款流程根据合同和支付渠道规则执行；退款成功后调整会员权益、留下可核对的审计记录，不影响法定/必要订单记录。
- **FR-028｜自动续费 [V1.3 候选]：** **非首发前提**。取得支付机构对应产品权限后才上线；明确签约、续费提醒、取消、失败补救；不得把一次性微信支付模拟成自动扣款。

**财务口径：** 套餐收款与商家顾客的餐饮交易必须使用不同的账单域和商户/订单标识；防止把平台会员费计入餐厅经营收入。

## 9. 模块需求：经营数据中心与数据标准化

### 9.1 数据来源与生命周期

- **FR-030｜内部系统接入 [V1.0]：** 从已有订单/商品/支付/退款/KDS 合法且授权地读取；内部数据走标准化适配器，不直接让 AI 执行任意 SQL。
- **FR-031｜来源登记 [V1.1]：** `source_id` 记录来源类型（POS/CSV/API）、文件批次、所属商户门店、上传人、导入时间、覆盖时间、原始记录数、成功数和失败数。
- **FR-032｜原始与标准层分离 [V1.1]：** 原始数据以访问控制及必要期限留存用于溯源；标准层写入统一模型；聚合指标单独计算，不覆盖源数据。
- **FR-033｜同步一致性 [V1.1]：** 同门店允许混合来源，但默认先提示时间范围重叠；优先同源订单 ID + 来源标识判定重复，对无法唯一匹配的跨来源数据标记冲突并要求人工确认，禁止凭金额/时间近似值静默合并。
- **FR-034｜数据质量分级 [V1.1]：** `完整 / 部分可用 / 不足以分析 / 存在冲突`；每条报告声明依据来源、覆盖时间、缺失字段及限制。

### 9.2 统一最小数据模型

| 实体 | 关键字段（示例） | 用途 |
|---|---|---|
| `merchant` / `store` | `tenant_id`、`store_id`、时区、营业日规则 | 隔离及归属 |
| `order` | `source_id`、`external_order_id`、`order_id`、`business_date`、`created_at`、`status` | 订单基础 |
| `order_item` | `order_id`、`product_id`、`quantity`、`item_amount`、`discount_allocated`、`refund_qty` | 销量与商品贡献 |
| `payment` | `payment_id`、`order_id`、渠道、状态、`paid_amount`、`paid_at` | 实收与对账 |
| `refund` | `refund_id`、`order_id`、`refund_amount`、状态、时间 | 部分/全额退款 |
| `product` | 商品名称、分类、成本口径及有效期 | 分类、成本与毛利 |
| `kds_event` | 订单/菜品、入队、开始、完成、取消时间 | 出餐效率（可选） |
| `inventory_event` | 入库、损耗、销售扣减、单位换算 | 备货/损耗（后续） |
| `data_batch` | 批次、文件哈希、状态、警告与覆盖范围 | 导入追溯 |
| `metric_snapshot` | 指标、时间窗、版本、口径、来源指纹 | 报告复现 |

所有金额统一用最小货币单位的**整数**（人民币分），数量使用明确单位与精度；数据库保存 UTC 时刻，并在报表根据门店时区转换。手机号等与分析无关字段在分析链路中默认剔除或脱敏。

### 9.3 经营指标口径（必须先定标准）

- **商品标价总额 GMV（展示定义）：** 有效交易行在优惠前的商品金额汇总；是否含运费、服务费另列，不混入。
- **实收营业额（核心）：** 在选定报表口径内，成功收款金额减去对应成功退款金额；预收款/储值充值不得未经区分直接计为餐饮营业收入。
- **订单数：** 以订单在约定时点达到「有效完成」状态计数；取消单不计，部分退款订单按业务定义保留订单但调整净额。
- **客单价：** 对应时间窗实收营业额 ÷ 有效订单数，分母为 0 时显示「—」。
- **销售数量：** 订单商品已完成数量扣除已退数量；套餐拆分需保留拆分规则版本。
- **毛利（条件性）：** 已知的销售净收入 − 对应销售商品成本；成本不完整时仅显示「已知成本测算」，**不得标为真实毛利或净利润**。
- **净利润：** 必须在人工、租金、水电、平台佣金、税费等费用口径完备时才提供，否则不生成。
- **出餐耗时：** 用业务事件时间计算，明确从「订单支付/下单/接单」至「菜品完成/整单完成」哪个起止点，指标不能混用。

**FR-035｜口径说明 [V1.1]：** 每个指标可展开看到公式、筛选条件、是否计入退款、来源完整度和生成时间；指标定义采用版本号，历史报告保留当时口径。

## 10. 模块需求：第三方 Excel / CSV 导入

### 10.1 用户流程

进入「数据接入」→ 选择原系统或通用模板 → 上传文件 → 预览表头 → 自动建议字段映射 → 用户校对 → 数据质量校验 → 查看异常/重复 → 确认导入 → 统一入库 → 生成可用指标 → 展示可分析范围。

### 10.2 功能规则

- **FR-040｜模板管理 [V1.1]：** 通用订单明细、商品销售、支付退款、成本四类模板；支持保存某商户的字段映射模板。
- **FR-041｜文件限制 [V1.1]：** 初始建议单文件 ≤20MB、≤50,000 行，可由配置调整；显示支持格式、字段示例和数据用途；超限提供拆分提示。
- **FR-042｜字段识别 [V1.1]：** 自动识别中文表头别名、日期/金额/数量格式；关键映射必须允许用户人工修正；AI 可辅助建议映射但不得无确认自动决定财务含义。
- **FR-043｜数据预校验 [V1.1]：** 校验金额非负/退款方向、日期范围、必填字段、币种/单位、重复订单、退款对应关系、状态值不明、门店归属和时区。
- **FR-044｜预览与回滚 [V1.1]：** 导入前列出成功/失败/警告数量及样例；提交后使用批次追踪；在不破坏已依赖其他批次数据的前提下支持撤销/冲正并触发重算。
- **FR-045｜重传幂等 [V1.1]：** 相同文件哈希及相同门店、相同数据范围再次上传不重复计入；数据有变化时显示「替换此批次 / 新增有效明细」选择与影响提示。
- **FR-046｜来源完整性 [V1.1]：** 若只有日汇总数据，允许展示日趋势但不得推导菜品级毛利和 KDS；若只有商品销量无支付信息，不宣称计算出实收额。
- **FR-047｜官方 API [V1.3]：** 仅通过合法开放接口和商家明确授权同步；针对每个供应商独立评估 API 可用性、授权范围、额度、费用、数据使用条款；不支持抓包绕过、模拟登录或未经许可爬取。

### 10.3 导入异常提示文案示例

> 已读取 12,580 行：12,300 行可导入、210 行疑似重复、70 行缺少支付状态。可先导入有效数据；含支付状态缺失的订单暂不纳入「实收营业额」分析。查看异常明细并修复后可重新导入。

## 11. 模块需求：历史经营分析（专业版）

- **FR-050｜日期分析 [V1.1]：** 支持最近 7/30/90 天与自定义时间窗；按营业日/自然日切换；指定门店；导出图表基础数据。
- **FR-051｜营业趋势 [V1.1]：** 实收、订单数、客单价，按日/周/月聚合；与上一可比周期对比，显示同期样本覆盖率。
- **FR-052｜商品分析 [V1.1]：** 销量/销售额排名、分类占比、低销量商品、优惠与退款影响；不将销量高直接解释为盈利高。
- **FR-053｜时段分析 [V1.1]：** 按本地小时/星期分析订单密度与销售贡献；跨凌晨归入正确营业日。
- **FR-054｜成本与毛利 [V1.1]：** 支持按单品设置原料成本及生效日期；提示成本覆盖率；只在覆盖率达到配置阈值（建议 ≥95%）时展示整体毛利估算，并始终标注未含哪些费用。
- **FR-055｜完整度提示 [V1.1]：** 任意指标出现来源缺失、导入冲突、跨期不完整时，在图表旁显示限制与修复入口。

## 12. 模块需求：AI 经营参谋（付费核心）

### 12.1 核心工作流

**标准流水线：** 定义分析时间窗 → 读取授权标准化数据 → 计算可复现指标 → 规则/统计异常候选 → 数据质量门控 → AI 解释和方案生成 → 安全校验 → 输出证据卡与行动建议 → 商家反馈 → 到期效果复盘。

### 12.2 诊断卡结构

一张诊断卡必须包括：

1. **问题标题：** 如「周末蔬菜出餐偏慢」，不得使用未经证实的「亏损严重」等表达。
2. **证据：** 样本量、统计期间、具体指标、基线、来源门店和覆盖度。
3. **推测原因：** 明确标注「可能原因」，区分观察事实与尚未验证的假设。
4. **优先级与影响：** 严重度、发生频率、潜在影响范围；不虚构损失金额。
5. **建议措施：** 具体动作、岗位、执行成本/难度、完成时间建议。
6. **观察指标：** 用哪项指标衡量改善效果、何时复查、有哪些混杂因素。
7. **数据限制与反馈：** 允许商家标记「有用/无用/不适用/已执行」，查看算法与数据依据。

### 12.3 首期诊断能力

| 诊断主题 | 触发数据 | 可能建议 | 首期要求 |
|---|---|---|---|
| 销售结构变化 | 7/30 天商品销量、金额、对比期 | 检查主推商品、套餐搭配 | P0 |
| 客单价变化 | 实收、有效订单数、时段 | 排查优惠变化、客群时段 | P0 |
| 时段波动 | 工作日/周末分布、可比时间窗 | 调整备货时段/人员安排 | P0 |
| 退款/取消异常 | 订单、退款原因（如有） | 核实差评、出品与收银流程 | P0 |
| 出餐积压 | KDS 完成事件（如有） | 分工及调度调整 | P1（依赖事件完整） |
| 毛利偏低 | 已知成本、销量、促销 | 核查成本、份量和定价 | P1（依赖成本质量） |
| 备货建议 | 长周期销量+库存+损耗 | 估计需求与安全库存 | P1（需足够历史数据） |

### 12.4 AI 的可信度规则

- **FR-060｜指标前置 [V1.2]：** 任何金额、比例、趋势结论引用预计算指标 ID 与口径版本；模型不能擅自虚构数字。
- **FR-061｜样本门槛 [V1.2]：** 异常检测可配置最小样本，首期建议至少 **7 个可比营业日和 30 笔有效订单** 才输出常规趋势诊断；不满足则提示「数据不足」，绝不硬推结论。
- **FR-062｜证据链 [V1.2]：** 保存 `report_id`、`metric_snapshot_id`、来源批次、数据时间窗、提示词版本、模型版本和结论引用；可追溯及复现关键计算。
- **FR-063｜区分事实/假设 [V1.2]：** 诊断明确标注「数据发现」「可能原因」「建议动作」「验证方式」；不以相关性冒充因果性。
- **FR-064｜敏感行为拦截 [V1.2]：** AI 仅生成建议或只读查询；不得直接发起退款、改价、删单、库存变更、营销触达。
- **FR-065｜质量校验 [V1.2]：** 输出 JSON Schema 检验、指标引用校验、敏感信息脱敏、无证据结论过滤，失败则回退到非 AI 指标摘要。
- **FR-066｜建议追踪 [V1.2]：** 商家可手动标记计划/已执行/不采纳；系统按相同口径查看前后变化，提示「受客流、天气、排班等影响，不能单凭变化认定因果」。

### 12.5 日报、周报与问数

- **FR-067｜自动日报 [V1.2]：** 在营业日关闭且支付/退款同步完成后的延迟窗口内触发（建议截止后 30～60 分钟，后端可配置）；报告包含实收、订单量、主要变化、最多 3 项行动建议。
- **FR-068｜周报 [V1.2]：** 商家设定周起始日；汇总可比趋势、异常变化、上周动作追踪；本周数据不完整时不自动宣称环比增长。
- **FR-069｜通知 [V1.2]：** 默认站内消息；微信订阅消息/短信/邮件按用户授权和平台规则配置，不承诺无条件推送到达。
- **FR-070｜自然语言问数 [V1.3]：** 仅通过预定义指标查询工具与只读 WebMCP；根据角色过滤财务明细和个人信息；回答应展示时间窗和数据源。
- **FR-071｜成本和配额 [V1.2]：** 按门店/计划/周期统计 tokens、任务次数和成本；缓存相同数据快照的报告；超限明确提示下期恢复/升级，不能静默超支。

### 12.6 AI 报告示例（示意数据，非真实门店结果）

> **发现：** 过去 7 个可比营业日，周末蔬菜菜品平均完成时间为 34 分钟，肉类为 17 分钟；蔬菜有 21% 的菜品完成时间超过 40 分钟。  
> **可能原因：** 在 KDS 记录中，蔬菜订单被集中后置处理；仍需门店确认炉位与工序安排。  
> **建议：** 将超过 15 分钟等待的蔬菜订单提高提醒优先级，在不影响食品安全与出品质量的前提下合并同品项烤制。  
> **复查：** 未来 7 天比较蔬菜 P90 出餐时间、整单完成时间，同时记录客流与岗位人数。

### 13.2 AI 经营参谋页

**页签：** 待关注问题 / 已处理 / 经营日报 / 周报 / 我的行动。

## 14. 平台运营后台

- **FR-084｜成本监控 [V1.2]：** 统计单商户 AI 成本、配额消耗、任务失败及异常高频调用，并设全局预算阈值/熔断。

## 15. 数据安全、合规与可靠性

### 15.1 安全底线

1. 多租户强隔离；高风险查询实施权限、门店范围与字段级校验；禁止通过前端传入 `tenant_id` 即越权读取。
2. 关键接口认证鉴权、签名/防重放（适用时）、访问限流、导入病毒/宏安全检查；拒绝不可信文件公式或代码执行。
3. 存储及传输加密、密钥分离、最小授权、访问日志、定期备份和恢复演练。
4. 原始导入文件、顾客手机号、账户信息遵循最小必要；AI 分析优先使用匿名/聚合数据，未经约定不作为训练数据。
5. 支持商户数据导出和注销申请，按合同及法律规定区分可删除数据与依法必须留存的交易记录。
6. 第三方数据接入必须验证商家授权及原系统的数据使用权限；通过第三方大模型处理数据时需评估处理目的、数据范围、委托处理协议和供应商条款。
7. 商业化前由法务/合规人员核验《个人信息保护法》及适用的生成式 AI、网络与支付监管要求；本 PRD 不替代法律意见。

### 15.2 非功能性目标（立项建议值，需压测确定）

| 维度 | 建议目标 | 解释 |
|---|---|---|
| 核心收银可用性 | 月度目标 ≥99.9% | 报表/AI 宕机不得扩大至收银链路 |
| 核心读写接口 | 常用场景 P95 <2s | 以标准网络与指定并发压测为准 |
| 当日概览延迟 | 常规 ≤60s | 标明最后刷新时间，异常可手动刷新 |
| 文件导入 | 20MB/5 万行以内异步处理 | 展示进度、错误和任务恢复能力 |
| AI 报告 | 异步、可取消/重试、可追踪 | 不在收银请求同步调用大模型 |
| 灾备与恢复 | 定义 RPO/RTO 并演练 | 建议先完成恢复预案后商用 |
| 可观测性 | 错误率、延迟、失败任务、成本 | 关键告警有人负责处理 |

## 16. 业务流程与关键状态

### 16.1 商家开通及付费

```text
注册商户 → 创建门店 → 免费运营
                  ├─ 仅收银 → 继续免费使用
                  ├─ 查看历史高级分析 → 升级专业版
                  └─ 数据满足诊断条件 → 查看预览 → 升级 AI 版
                                                        ↓
                            创建平台订阅订单 → 商家主动支付
                                                        ↓
                                  支付确认/验签/幂等 → 生效
                                                        ↓
                                       到期提醒 → 续费或降级
                                                        ↓
                                      基础收银继续正常运行
```

### 16.2 AI 诊断任务

```text
数据到达 → 去重/校验 → 指标快照 → 规则发现候选异常
                                      ↓
                                数据门槛判断
                           ├─ 不足 → 提示补数据
                           └─ 满足 → AI 解释与建议
                                      ↓
                               输出核验与脱敏
                                      ↓
                             诊断卡/报告归档
                                      ↓
                           商家反馈 → 效果复盘
```

### 16.3 失败与降级策略

- 支付通知丢失：主动查单恢复，不能凭前端「支付成功」提示发放权益。
- AI 服务超时/限额：展示确定性指标及明确提示，不阻塞收银。
- 文件数据冲突：本批次进入待处理队列，不能悄悄覆盖既有经营账。
- 报告过期：标记数据更新时间和版本，避免把旧结论当成今日事实。
- 平台会员到期：关闭高级新分析，核心经营权限维持，数据不被删除。

## 19. 研发交付与实施建议

### 19.1 依赖清单

1. **先做现状盘点：** 核查已有 Java 后端、OpenAPI、用户体系、订单/支付/KDS 事件、门店模型、收银故障隔离；标记可复用模块与需要改造的数据库表。
2. **再做权限与计费底座：** 确认租户隔离、功能权益、账单状态机和幂等回调，形成安全的收费边界。
3. **再做统一经营口径：** 先与自身门店真实订单对账；统一指标引擎完成后接 CSV，最后才开放 AI 生成结论。
4. **最后做 AI：** 优先 4 类有证据的诊断；不把大模型塞入关键收银事务中。

### 19.2 建议工程模块（逻辑划分，不要求一开始拆微服务）

`pos-core` / `tenant-identity` / `entitlement-billing` / `data-adapter` / `metric-engine` / `ai-insight` / `report-scheduler` / `ops-console`。

**架构原则：** 先在 Java 单体中采用边界明确的模块化架构；只有在业务规模、可靠性和部署需求证明确有必要时才拆分服务。继续复用现有只读 WebMCP 数据能力作为受控工具层，严禁把完整数据库权限直接授予模型。

### 19.3 交付物

- 产品侧：高保真原型、菜单/套餐配置表、指标口径手册、角色矩阵、试点反馈表。
- 研发侧：现有 OpenAPI 差异清单、数据模型与迁移计划、服务端权益接口、导入接口契约、AI JSON Schema、任务与审计设计。
- 测试侧：本 PRD 的 UAT、财务对账样本、多租户越权测试、支付异常回放、模型输出安全回归。
- 运营侧：订阅与退款规则、隐私政策/数据处理协议、导入教学、客户支持方案、产品分析看板。

## 20. 风险、应对与发布门禁

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 现有系统非多租户架构 | 越权、数据污染 | 先完成隔离测试，禁止提前开放多商家 |
| 内外部数据口径不一致 | AI 结论不可信 | 统一指标计算、批次溯源、报表注释 |
| 第三方 API 不可用或费用高 | 产品承诺落空 | Excel/CSV 为首发能力；API 逐家签约评估 |
| AI 幻觉/错误归因 | 商家经营损失 | 确定性指标、最小样本、证据引用、人工反馈 |
| 价格低于服务成本 | 越用越亏 | 配额、缓存、成本看板、套餐毛利跟踪 |
| 收银受报表升级牵连 | 商家无法营业 | 物理/逻辑故障隔离，回滚预案 |
| 个人信息及外部数据风险 | 投诉、法律与声誉损失 | 最小必要、授权、脱敏、审计、合规评估 |
| 营销期数据太少 | AI 只能套模板 | 明确「数据不足」空态，优先卖好基础报表 |

**发布门禁：** 收银核心回归通过、支付对账通过、租户隔离测试通过、导入对账误差可解释、AI 无证据结论拦截通过、隐私/合同文件上线、监控和备份恢复可用，才能向真实商户逐步放量。

## 21. 首批试点与后续评审议题

**试点建议：** 以自有门店做 1 家内部长期对账样本，再选择 2 家使用本系统 POS 的商家、2 家导入第三方数据的商家。分别记录首次价值时间、上传难度、老板实际采纳的建议、成本和续费意愿。

**下次评审必须明确：**

1. 现有 Java 收银后台与小程序账号体系、POS 表结构及权限模块现状。
2. 目前收银款流向与 SaaS 会员收款主体、支付商户号之间的隔离方案。
3. 首期支持的第三方导入报表样本与准确字段列表。
4. 套餐最终价格、单店与多店规则、试用/退款政策及 AI 配额。
5. 仅生成建议还是允许可撤销的半自动执行——本版仅建议、不执行。

|---|---|---|
