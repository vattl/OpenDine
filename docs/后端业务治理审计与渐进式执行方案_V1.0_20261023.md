## 1. 执行摘要

当前后端不是“尚未开始治理”，而是已经完成了若干关键闭环，但治理成熟度不均衡：支付与 KDS 的可靠性建设明显领先，订单并发、审批安全、权限最小化、统一价格模型和跨域待决态仍落后。

综合结论：**建议批准进入阶段 0～2，暂不直接启动全量重构。** 先修复两个 P0 安全/一致性问题，再通过兼容窗口逐步收敛接口契约。

优先顺序如下：

1. **P0：审批授权严格绑定与令牌存储安全**。当前密码/PIN审批令牌允许业务对象占位、金额额外放宽 50 元，二维码审批令牌明文短期落库；这与目标方案的“对象、金额、动作严格绑定”冲突。
2. **P0：订单写入版本控制与强幂等**。订单已有 `revision` 列，但收银端加菜、退菜、改价、优惠、结账等未统一要求 `expectedVersion`；`X-Client-Request-Id` 缺失时会直接执行，不能阻止多终端陈旧写入。
3. **P0：权限映射收敛**。内置映射共 370 条，其中 73 条是单一 `cashier:operate`，收银前缀 57 条中 51 条包含该粗粒度权限；数据库映射与代码兜底并存，存在策略漂移面。
4. **P1：统一价格明细与冲突规则**。菜品和套餐价格已经做服务端校验，但价格计算仍分散在下单、加菜、金额重算、支付结算、后台改价等多条链路，缺少统一 `PriceBreakdown` 和优惠叠加矩阵。
5. **P1：统一结果语义与待决中心**。支付/退款/KDS 各自已有 `UNKNOWN`、补偿任务或命令台账，但没有跨域的待决查询模型，错误响应字段也不统一。
6. **P1/P2：KDS 兼容层退役及交接班/打印权限细分**。KDS 云端唯一权威已经成立，旧复制链也已 fail-closed；剩余重点是兼容路由、旧表和死信链的可观测退役，而不是重写 KDS。

建议总工期为 **8～11 周**（单后端主力 + 测试支持）；若权限治理、价格治理和 KDS 退役由不同负责人并行，在契约先冻结的前提下可缩短至 **6～8 周**。任何阶段都必须以独立 Work Item 进入 `/work`，不得把本文直接当作生产代码修改授权。

## 4. 详细审计发现

### F-01 审批令牌未严格绑定，且二维码令牌明文落库

- 严重度：**Critical / P0**
- 对应目标缺口：G-02
- 当前事实：
  - 密码/PIN授权在缺少 `bizId` 时写入 `N/A`。
  - 密码/PIN授权将 `max_amount` 设置为申请金额 + 50 元。
  - 核销时 `N/A`、空值、`ID:*` 被视为占位值，不参与资源强绑定。
  - 审批人可通过较宽泛的 `order:operate` 等权限获得批准资格，而非严格动作级审批权限。
  - 二维码批准后将原始 `approvalToken` 写入 `token_value`，轮询接口再返回明文；核销时才清空。
  - 未发现针对 `/cashier/access/authorize` 的失败频率限制或 PIN 暴力尝试锁定。
- 风险：令牌可被用于不同订单、不同金额或不同操作上下文；数据库读权限泄露可直接暴露短时高权限令牌；暴力猜 PIN 缺少独立防护。
- 目标状态：
  - 新客户端必须提供 `resourceType + resourceId + exactAmount + permissionCode + operatorId + shopId + terminalId + requestId`。
  - 金额默认精确相等；确需容差时由具体策略显式配置，不能全局 `+50`。
  - 仅动作对应的 `*:approve` 或明确审批角色可以批准。
  - 数据库只保存令牌哈希；跨实例领取使用一次性兑换码、短期加密信封或服务端原子领取，不保存可直接使用的明文业务令牌。
  - 失败授权按账号、门店、终端和来源 IP 组合限速，并记录安全审计。
- 主要修改面：
  - `ApprovalService`、`AccessContext`、`CashierAccessController`。
  - `t_access_approval` 迁移与历史令牌清理。
  - 所有调用 `validateAndConsume` 的敏感操作控制器。
  - OpenAPI、API.md、收银端契约交接。

### F-02 权限仍以 `cashier:operate` 为主，映射存在双权威

- 严重度：**High / P0**
- 对应目标缺口：G-01、G-04
- 当前事实：
  - 内置映射共 370 条，单一 `cashier:operate` 73 条。
  - `/cashier/*` 内置映射 57 条，其中 51 条包含 `cashier:operate`。
  - 加菜、退菜、退款、改价、优惠、结账、反结账、支付、打印、交接班和 KDS 投递大量共用一个入口权限。
  - 敏感订单操作当前采用“入口 `cashier:operate` + Controller 二次授权”的兼容设计；测试明确要求不得直接把入口改成敏感权限，否则普通收银员连发起审批都无法做到。
  - `SysInterceptor` 先查数据库 `t_api_permission`，未命中再查代码内置映射。数据库可运行时修改、代码也可新增，两者没有自动差异门禁。
  - `|` 表示任一权限即可通过，当前存在 51 条多候选映射，需要逐条确认是否过度放权。
- 风险：最小权限难以表达；权限变更可能只改 DB 或只改代码；不同环境迁移状态不同会出现不同行为。
- 目标状态：
  - 建立动作级权限词汇表，例如 `order:create/add-item/refund/change-price/discount/checkout/reopen`、`payment:collect/reverse/refund`、`print:dispatch/reprint`、`shift:open/handover/cash-movement`、`kds:proxy/read/recover/config`。
  - 保留“基础进入权限 + 可发起审批”的能力，但由统一授权决策器返回 `ALLOW / REQUIRE_APPROVAL / DENY`，不再在各 Controller 拼接二次校验。
  - 将数据库映射定义为运行时权威，代码仅保留生成清单/启动校验，不再静默兜底不同策略；或反向采用代码生成迁移，二者必须二选一。
  - CI 对 Controller 路由、OpenAPI、权限目录和迁移数据做全量差异检查。

### F-03 订单 `revision` 存在但未成为通用写契约

- 严重度：**High / P0**
- 对应目标缺口：G-08
- 当前事实：
  - `t_order` 和 `Order` 已有 `revision`。
  - KDS V2 会增加订单 revision，但收银端订单写接口未统一接收 `expectedVersion`，也未执行 `WHERE id=? AND revision=?` 的 CAS 更新。
  - 加菜、退菜、改价、优惠等链路有的使用订单行锁，有的先普通查询再更新；它们能处理部分服务端并发，却不能识别“客户端看到旧版本后提交覆盖”的业务冲突。
- 风险：多收银终端或收银端/KDS/后台同时操作时，陈旧页面可能覆盖新金额、优惠或状态；冲突只能表现为金额漂移或后置校验失败。
- 目标状态：
  - 所有订单/桌台写命令携带 `expectedVersion`。
  - 服务端锁定订单后校验版本，并在成功提交时单调递增。
  - 冲突返回 HTTP 409、`businessCode=ORDER_VERSION_CONFLICT`、`latestVersion` 和安全的最新摘要。
  - KDS 引发的订单版本变化与收银业务版本语义对齐，避免两个版本计数器互相覆盖。

### F-04 写接口幂等键仍是可选，且订单与桌台头字段不统一

- 严重度：**High / P0**
- 对应目标缺口：G-05、G-08
- 当前事实：
  - 订单写请求支持 `X-Client-Request-Id`，具备请求指纹和 24 小时响应重放。
  - 该请求头为空时 `CashierClientRequestService` 直接执行操作。
  - 桌台命令使用 `Idempotency-Key` / `X-Request-ID`，与订单写入不一致。
  - 不是所有金额/状态写接口都经过同一幂等执行器。
- 风险：客户端超时重试仍可能重复加菜、重复退款或重复状态变更；跨模块 SDK 无法形成统一重试规则。
- 目标状态：
  - 新版本客户端对所有业务写命令强制 `Idempotency-Key`。
  - 兼容期同时接受旧头并回传弃用提示，服务端规范化为一个 `idempotencyKey`。
  - 幂等记录绑定 `shopId + actorId + operation + resourceId + fingerprint`，不能只按门店和键复用。
  - 明确处理中、成功、拒绝、冲突、未知的重放语义。

### F-05 业务不变量基线漂移

- 严重度：**High / P0（治理阻断）**
- 对应目标缺口：G-03
- 当前事实：
  - `.ai/project/business-rules.json` 已记录 3 条支付不变量和 1 条 KDS 不变量。
  - `docs/project/BUSINESS_RULES.md` 仍声明没有项目业务不变量。
  - 订单首单时间、桌台金额等价于订单净应付、套餐子行不重复计价、审批严格绑定等核心规则没有进入统一耐久基线。
- 风险：不同任务或分支选择不同基线，造成已经修复的功能再次回退。
- 目标状态：一个业务不变量权威源，至少覆盖订单、价格、支付、退款、桌台、班次、打印、KDS 八个域；每条包含 ID、所有者、验证方式和关联场景。

### F-06 响应结构和业务结果语义不统一

- 严重度：**Medium-High / P1**
- 对应目标缺口：G-05
- 当前事实：
  - 通用 `R.error(String)` 默认业务码为 500，许多可预期的校验失败因此表现为 `code=500`。
  - `ApiException` 路径返回真实 HTTP 状态和 `error/error_code`，普通 `R.error` 通常仍为 HTTP 200 + body code。
  - 未形成统一的 `SUCCEEDED / REJECTED / CONFLICT / PENDING / UNKNOWN` 字段。
  - `traceId` 主要在未处理异常和鉴权响应中存在，业务拒绝通常没有。
- 风险：客户端只能解析中文消息判断下一步；无法统一决定重试、刷新、查单或人工处理。
- 目标状态：
  - 新错误包统一为 `businessCode/message/traceId/resultStatus/retryable/resolutionType/latestVersion/blockingReasons/details`。
  - 保留旧 `code/msg` 作为兼容字段，在版本窗口后淘汰。
  - HTTP 状态表达协议层结果，`resultStatus` 表达业务终态。

### F-07 价格已做后端校验，但仍缺单一价格权威模型

- 严重度：**Medium-High / P1**
- 对应目标缺口：G-07
- 当前事实：
  - 普通菜、套餐头和套餐子行已有严格价格/在售/库存校验，客户端不能随意提交 0 元、负数或偏离门店售价的金额。
  - 收银快速开单仍先接收 `total_price`，再由下游校验，而不是请求商品标识后由服务端报价。
  - 金额逻辑分布在 `OrderController`、`OrderAmountRecalculationService`、`PaymentSettlementService`、后台订单详情和多个工具类。
  - 优惠券、手工优惠、夜间九折、赠送菜、服务费、打包费和配送费没有统一冲突矩阵或分摊明细。
  - 接口响应没有统一 `PriceBreakdown`，无法解释原价、每项优惠、费用、退款和最终应付的来源。
- 风险：同一订单在列表、桌台、预结单、支付和报表之间可能出现计算路径不一致；新增营销规则会继续复制条件分支。
- 目标状态：
  - 建立 `OrderPricingService` 作为唯一计算入口，输入服务端加载的商品快照和规则快照。
  - 建立 `PriceBreakdown`：`goodsSubtotal/serviceFee/packagingFee/deliveryFee/discounts/refunds/giftPayments/payable/rounding/ruleVersion`。
  - 建立显式优惠优先级与互斥矩阵；所有渠道共用同一报价结果或持久化快照。

### F-08 各域已有待决机制，但缺统一待决中心

- 严重度：**Medium-High / P1**
- 对应目标缺口：G-05
- 当前事实：
  - Native/付款码/JSAPI 有 `CREATING/USERPAYING/UNKNOWN` 和主动查单。
  - 微信退款有 REQUESTED 台账和 5 分钟补偿任务。
  - 打印有 `PENDING_DEVICE`，KDS 有命令台账、事件和投递状态。
  - 没有按门店、终端、班次、订单统一查询“需要继续查单/重试/人工处理”的 API。
- 风险：收银端需分别拼装多个域的状态；班次交接和关账难以证明所有未知事项已闭环。
- 目标状态：新增只读聚合的 `PendingActionQueryService`，先不改各域状态机；按统一模型输出 `domain/resource/action/status/age/nextRetryAt/retryable/resolutionType/owner`。

### F-09 KDS 主架构已收敛，但兼容面尚未退役

- 严重度：**Medium-High / P1**
- 对应目标缺口：G-06
- 当前事实：
  - 云端唯一业务权威、V2命令台账、事件游标、查询参数 token 拒绝、旧写链 fail-closed 均已落地。
  - `CashierKdsDeliveryController` 同时暴露 `/cashier/kds`、`/admin/cashier/kds`、`/api/admin/cashier/kds` 三组前缀，并为多项子路由保留别名。
  - `/admin/kds/device/proxy-login` 和 `/proxy-command` 已返回停用语义，但路由和权限映射仍存在。
  - replication 写入口、死信入口、兼容表和 `authority_mode='legacy'` 仍作为过渡能力保留。
  - 跨仓库 KDS-CA-1.3 明确 Android Keystore 真机验收、三进程组合故障矩阵和旧表退役仍未完全关闭。
- 风险：文档虽统一，运行面仍存在多条看似可用的入口；兼容层可能被新客户端继续依赖，导致永久债务。
- 目标状态：建立兼容路由注册表、调用量指标、最后使用版本和删除日期；完成零调用观察期、死信清零/裁决后再删除路由和表。

### F-10 打印与交接班能力成熟，但操作权限仍过粗

- 严重度：**Medium / P2**
- 对应目标缺口：G-01、阶段 4
- 当前事实：
  - 打印调度、模板、任务和补打已经集中化。
  - 收银端后厨打印、统一调度、开班、交班、现金移动、班次报表仍大多只要求 `cashier:operate`。
- 风险：能收银的员工默认也能补打、现金移动或执行交接班，职责分离不足。
- 目标状态：拆分 `print:dispatch/reprint`、`shift:open/handover/view`、`cash:movement`；敏感现金差异走严格审批上下文。

### F-11 可观测性未覆盖治理目标

- 严重度：**Medium / P2**
- 当前事实：已有鉴权拒绝审计、支付结构化日志、KDS 指标，但未发现统一的 `legacy_permission_hit`、`stale_write_conflict`、`approval_binding_reject`、`pending_oldest_age`、`compat_route_hit` 指标。
- 风险：无法判断兼容入口是否可删除，也无法量化多终端冲突和待决积压。
- 目标状态：在迁移前先加指标，再依据真实调用量收紧权限和删除兼容层。

### F-12 API 入参类型边界偏弱

- 严重度：**Medium / P2**
- 当前事实：收银订单和审批大量使用 `Map<String,Object>` 手工读取字段；字段别名、必填性、金额精度和版本约束分散在方法内部。
- 风险：OpenAPI 与实现容易漂移，静态分析和参数校验覆盖不足，新增字段会继续堆叠条件分支。
- 目标状态：新契约使用显式 Command DTO + Bean Validation；兼容适配器只负责把旧字段转换为新命令，不进入业务服务。

## 5. 目标架构与统一契约

### 5.1 统一动作上下文

所有敏感或可重试写命令应在进入业务服务前形成：

```text
ActionContext
├─ requestId / traceId / idempotencyKey
├─ actorId / authorizerId / shopId / terminalId / shiftId
├─ operation / resourceType / resourceId
├─ expectedVersion
├─ reasonCode / reasonText
└─ approvalToken（只在边界出现，服务层使用核销结果）
```

控制器只完成认证上下文装配、DTO 校验和兼容字段转换；权限决策、审批核销、版本检查、幂等占位和审计写入由统一命令门面完成。

### 5.2 统一结果语义

```json
{
  "code": 409,
  "msg": "订单已被其他终端更新",
  "businessCode": "ORDER_VERSION_CONFLICT",
  "resultStatus": "CONFLICT",
  "traceId": "...",
  "retryable": false,
  "resolutionType": "REFRESH_RESOURCE",
  "latestVersion": 18,
  "blockingReasons": [],
  "details": {}
}
```

状态限定为：`SUCCEEDED`、`REJECTED`、`CONFLICT`、`PENDING`、`UNKNOWN`。兼容期保留 `code/msg/error_code`。

### 5.3 统一订单写入协议

- 请求必须包含 `Idempotency-Key` 和 `expectedVersion`。
- 服务端顺序固定：幂等占位 → 鉴权/审批 → 锁定订单 → 校验版本 → 校验业务状态 → 执行 → 增加版本 → 写审计/事件 → 提交 → 返回快照。
- 同幂等键同指纹返回首个结果；同键不同指纹返回冲突。
- 版本冲突不自动覆盖，也不以“最后写入者获胜”静默处理。

### 5.4 统一价格模型

- 请求只表达商品、数量、选项、营销凭据和操作意图。
- 服务端加载门店商品/套餐/营销/费用规则并产生报价。
- 下单保存价格快照与规则版本；支付使用同一订单快照重新校验，不在支付层重新发明优惠规则。
- 桌台、列表、预结单、支付、打印、报表均消费同一 `PriceBreakdown`。

### 5.5 统一待决模型

先建设只读聚合，不强行合并各域状态表：

```text
PendingAction
├─ domain: PAYMENT | REFUND | PRINT | KDS | ORDER_FULFILLMENT
├─ resourceType / resourceId / orderNo
├─ status: PENDING | UNKNOWN
├─ createdAt / updatedAt / ageSeconds / nextRetryAt
├─ retryable / resolutionType
├─ shopId / terminalId / shiftId / owner
└─ safeSummary
```

## 6. 分阶段执行计划

### 阶段 0：建立正式 Work Item 与基线收敛（3～5 人日）

**目标：** 先形成后续所有改造的权威输入，阻断再次分支回退。

任务：

1. 创建总治理 Epic/Work Item，并拆成下述独立 Work Item；为每项建立 Impact Map、Scenario Matrix 和 Delivery Gate。
2. 合并 `docs/project/BUSINESS_RULES.md` 与 `.ai/project/business-rules.json`，确定单一权威和生成/校验方式。
3. 补充业务不变量：
   - `INV-ORDER-001`：加菜不得改变首单 `order_time`。
   - `INV-ORDER-002`：成功写入必须单调增加订单版本。
   - `INV-PRICE-001`：最终应付金额仅由后端价格模型产生。
   - `INV-TABLE-001`：桌台待结金额等于同店同桌全部未结订单净应付之和。
   - `INV-COMBO-001`：套餐头计价、组件不重复计价且必须可追溯父行。
   - `INV-APPROVAL-001`：审批令牌严格绑定动作、对象、金额、操作者和门店，只能核销一次。
4. 生成当前接口、权限码、路由别名、错误码和状态值清单，纳入版本控制。
5. 建立兼容策略：最低客户端版本、警告头、截止日期、回滚方式。

验收：

- 两个业务规则文件不再互相矛盾。
- 每个后续 Work Item 的依赖、影响层和 API 消费者明确。
- `IMPLEMENTATION_READY` 仍为 `NO`，直到对应 Work Item 的 ready gate 单独通过。

### 阶段 1：审批安全闭环（5～7 人日）

**目标：** 消除可跨对象/跨金额复用与明文令牌存储。

垂直切片：

1. 先写 RED 测试：占位 `bizId`、金额不相等、操作不相等、终端不相等、重复领取、暴力 PIN 均失败。
2. 扩展 `AccessContext` 和审批表，新增动作/对象/精确金额/终端/班次/原因字段；准备历史数据兼容标记。
3. 实现审批策略版本：旧客户端仅在明确兼容窗口走 `legacyBinding=true`，记录指标；新客户端一律严格。
4. 用哈希 + 原子一次性领取替代 `token_value` 明文；迁移后清空历史明文。
5. 实现动作级审批权限和授权频率限制。
6. 更新 OpenAPI、API.md 和前端 Contract Handoff。

验收：

- 任意绑定字段不一致均拒绝，且不消耗令牌。
- 成功核销为 CAS 一次性；并发两次仅一个成功。
- 数据库、日志和 API 列表响应均不出现可直接使用的审批令牌明文。
- 旧兼容调用可量化并可按版本关闭。

### 阶段 2：权限最小化与单一权威（7～10 人日）

**目标：** 从角色式大权限迁移到动作权限，同时不破坏“普通收银员发起审批”。

垂直切片：

1. 冻结权限词汇表和动作决策表。
2. 建立 `AuthorizationDecisionService`，输出 `ALLOW/REQUIRE_APPROVAL/DENY`。
3. 先迁移退款、改价、优惠、反结账四个高风险动作；入口仍允许收银端访问，但业务决策必须精确。
4. 再迁移支付撤销、现金移动、补打、交接班、KDS恢复。
5. 选定权限映射单一权威，并增加启动校验和 CI 差异门禁。
6. 迁移角色权限数据；先影子判定并记录差异，再切换强制模式。

验收：

- 低权限收银员能发起审批但不能绕过审批完成敏感操作。
- 具备单个动作权限的员工不能获得同域其他动作。
- DB、内置清单、OpenAPI 和权限文档零差异。
- 所有 `|` 多候选映射完成书面裁决。

### 阶段 3：订单版本与强幂等（7～10 人日）

**目标：** 多终端并发下拒绝陈旧写入，所有可重试命令可安全重放。

垂直切片：

1. 定义统一 `OrderCommandContext` 和版本冲突响应。
2. 先改加菜、退菜、改价、优惠，再改结账/反结账、挂单/取消挂单、人数更新。
3. 对每次业务写执行订单版本 CAS；明确 KDS 变更是否增加同一版本。
4. 统一 `Idempotency-Key`，兼容旧 `X-Client-Request-Id` / `X-Request-ID`。
5. 幂等记录补充资源、动作、操作者和结果状态；处理中请求返回 `PENDING` 而不是泛化 409 文案。
6. 为并台主从单制定版本锁顺序和冲突摘要。

验收：

- 两个终端基于同一版本同时加菜，仅一个成功，另一个得到可刷新恢复的 409。
- 相同幂等键同请求重放不产生第二条明细/退款/支付。
- 相同键不同请求稳定冲突。
- 版本冲突不会改变订单、桌台金额、库存、支付尝试或 KDS 投影。

### 阶段 4：统一价格与优惠规则（8～12 人日）

**目标：** 所有展示和支付共享同一可解释价格结果。

垂直切片：

1. 建立只读 `PriceBreakdown`，先从现有订单数据反算并与当前金额比对。
2. 建立优惠规则矩阵，裁决优惠券、手工优惠、九折、赠送菜的叠加/互斥和分摊。
3. 建立 `OrderPricingService.quote`，由服务端基于商品/套餐/门店规则计算。
4. 收银快速开单与加菜改为提交商品意图；兼容期仍接受客户端金额，但只作断言，不作计算源。
5. 订单保存规则版本和价格快照；支付、桌台、打印、报表消费统一明细。
6. 增加历史订单兼容：没有快照时标记 `LEGACY_RECONSTRUCTED`，不得伪造精确分摊。

验收：

- 套餐 108 + 单品 8 在订单、桌台、预结单、支付和打印均为同一应付额。
- 加菜、退菜、并台、优惠、退款后各金额字段满足不变量。
- 所有优惠项能说明规则来源、金额和互斥原因。

### 阶段 5：统一结果语义与待决中心（8～12 人日）

**目标：** 客户端能可靠决定“结束、刷新、等待、查单、重试或人工处理”。

垂直切片：

1. 建立错误/结果 envelope 和兼容序列化器。
2. 先迁移支付与退款，再迁移订单、打印和 KDS。
3. 建立只读待决聚合 API，汇总支付尝试、退款请求、打印任务、KDS命令和履约重试。
4. 将交班/日结前置检查接入待决摘要，定义硬阻断与软警告。
5. 增加待决龄、重试次数、最终处置和人工归属指标。

验收：

- 每个非成功结果都有稳定 `businessCode/resultStatus/resolutionType`。
- 收银端无需解析中文文案决定查单或重试。
- 交班可明确列出所有尚未闭环事项。

### 阶段 6：KDS、打印、班次收口及遗留退役（5～8 人日 + 观察期）

**目标：** 删除无调用兼容层，完成真实故障恢复验收和操作权限细分。

垂直切片：

1. 对所有 KDS 兼容前缀、代理停用路由、replication 入口加命中指标与客户端版本标签。
2. 完成 Android Keystore 真机验收和云端/收银/KDS 三进程组合故障矩阵。
3. 清理或裁决旧 replication dead letter，确认所有门店为 cloud authority。
4. 经观察期零调用后分两次发布：先 410/弃用，再删除路由和权限映射；最后删除旧表/任务。
5. 细分补打、现金移动、交接班和 KDS恢复权限。
6. 建立打印失败、班次差异、KDS pending/unknown 的运营处置手册。

验收：

- 新客户端仅使用正式云端 Token、`/kds/v2/commands`、命令结果查询、事件/WS和只读 bootstrap。
- 旧路由删除前有完整零调用证据和回滚路径。
- 云不可达时代理不本地承诺业务成功。
- 观察期内没有无法解释的 UNKNOWN 超过阈值。

## 9. 数据迁移与发布策略

### 9.1 迁移原则

- 只新增后切换，禁止一次发布同时删除旧字段和旧语义。
- 所有迁移幂等；大表变更评估锁表时间并设计回滚。
- 历史订单不能假装具备新价格快照；使用明确来源标记。
- 审批明文令牌迁移必须先停止新写入，再清空旧值并验证无残留。
- 权限迁移先影子判定、记录差异，再强制；不得直接批量替换 `cashier:operate`。

### 9.2 四步发布

1. **Observe**：加字段、指标和影子计算，不改变旧客户端结果。
2. **Dual-read / controlled dual-write**：新契约生效，旧契约经适配器进入同一服务。
3. **Enforce**：按客户端最低版本强制版本、幂等、审批和精细权限。
4. **Retire**：零调用观察期后删除兼容路由、字段、任务和表。

### 9.3 回滚要求

- 每个阶段独立开关，开关只允许回退“强制校验”，不能回退支付/KDS业务权威。
- 数据库回滚不得删除新写入证据；优先前滚修复。
- KDS 永远保持云端唯一权威，不提供“临时切回收银本地权威”的回滚方案。

## 11. 测试、文档与交付门禁

每个涉及 API 的 Work Item 必须：

1. 同步更新 `docs/openapi.yaml` 与 `docs/API.md`。
2. 更新消费者 Contract Handoff，明确前端字段、兼容期和错误处理。
3. 执行目标单元/集成测试、场景矩阵和安全审计。
4. 执行全量 `mvn clean package -DskipTests` 生成可运行 JAR；这只是构建证据，不等于验收。
5. 运行 `.ai/scripts/gate.py work --phase ready|accept`，分别证明可实施和可验收。
6. 将 `ACCEPTED`、`INTEGRATED`、`RELEASED` 分开记录。

建议的持续门禁：

- Controller 路由必须在权限映射和 OpenAPI 中存在。
- 权限码必须在权限目录中注册且有默认角色裁决。
- 所有订单写 API 必须声明 `Idempotency-Key` 和 `expectedVersion`。
- 所有金额响应必须引用统一 `PriceBreakdown` 或明确历史来源。
- 禁止新增 `R.error(String)` 作为可预期业务失败。
- 禁止新增 KDS 兼容别名或 replication 写路径。

## 12. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 直接细分权限导致普通收银无法发起审批 | 高 | 使用统一决策器，分离“进入动作”与“最终批准” |
| 强制版本后旧客户端大量 409 | 高 | 先返回 revision、影子记录缺失率，再按最低版本强制 |
| 强幂等增加数据库热点 | 中 | 资源+动作分区键、唯一索引、短事务、定期归档 |
| 价格服务切换引发历史金额变化 | 高 | 先影子比对；只对新订单启用快照；历史单明确重建来源 |
| 清理 KDS 兼容路由误伤存量设备 | 高 | 命中指标、客户端版本、410 过渡、观察期、可前滚恢复 |
| 统一错误模型破坏旧客户端 | 中 | 双字段兼容，按客户端版本逐步停用旧字段 |
| 审批令牌移除明文后跨实例轮询失败 | 高 | 原子一次性兑换或短期加密信封；做多实例并发验收 |

## 13. 立即执行建议

建议下一步只启动三个 Work Item，并按顺序完成：

1. **业务不变量与治理基线收敛**。
2. **审批上下文严格绑定 + 明文令牌移除**。
3. **订单 `expectedVersion` + 强幂等契约**。

完成这三项后再推进权限大规模迁移和统一价格服务。原因是权限和价格改造都会触碰大量订单写链；如果没有先建立严格审批、版本冲突和幂等基础，后续并行开发会继续制造难以定位的覆盖与回退。
