# Implementation Design — WI-017

## Root Cause

活动键唯一约束正确阻止了两个并发请求同时创建支付尝试，但冲突请求只读取一次胜出记录。当胜出记录仍为 `CREATING` 时立即返回 `40931`，把短暂、正常的幂等竞争暴露成收银失败。

## Root Fix / Owner

仅在捕获 `DuplicateKeyException` 后，对同一活动键执行有界、短间隔读取。若胜出记录进入未过期的 `ACTIVE` 且金额一致，返回其现有二维码并标记 `reused=true`。等待超时、记录消失、金额不一致或进入不确定状态时，保留现有安全错误。

## Reliability Boundaries

- 不重试插入，不调用第二次微信下单。
- 等待严格有界，避免无限占用请求线程。
- 线程中断时恢复中断标志并停止等待。
- 不改变支付成功判定、回调、查单和关单路径。

## Contract / Compatibility

请求和响应字段不变。行为向后兼容：部分原返回 `40931` 的短暂并发请求现在返回首个请求的成功二维码；超出等待窗口的响应保持不变。

## Verification Strategy

先写失败单测模拟唯一键竞争及胜出记录从 `CREATING` 到 `ACTIVE`，证明旧实现返回 `40931`；再实现最小修复，验证只返回同一二维码且不调用微信客户端。补充持续 `CREATING` 的超时用例并执行全量测试和 JAR 打包。
