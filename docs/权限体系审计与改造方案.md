## 2. 现状全景（已验证事实）

### 2.1 鉴权链（SysInterceptor，fail-closed）

```
请求 → ① JWT 校验（401）
     → ② 查角色权限集（t_admin_role → t_role_permission → t_permission）
     → ③ 路径→权限码映射（DB 优先，未命中回退代码内置）
     → ④ 门店范围校验（非 HQ 必须 allowedShopIds 包含 shopId，否则 4003）
     → ⑤ 放行 / 403 权限不足 / 4003 门店越权
```

- **AUTHENTICATED_ONLY_PATHS**（6 条，仅登录即可）：/admin/me/permissions、/admin/me/shops、/admin/app/version、/admin/push/device/*、/admin/push/preference
- **ADMIN_SHOP_CONTEXT_EXEMPT_PREFIXES**（13 条，豁免门店上下文解析）：/admin/me/、/admin/modifyPassword、/admin/shop/*、/admin/rbac/、/admin/administrator/、/admin/config/、/admin/log/、/admin/app/version、/admin/push/device/unregister、/admin/unit/、/admin/order/auto-accept、/admin/announcement/
- **失败关闭**：`required == null && 非白名单 → 直接 403 "接口权限未配置"`
- **`|` 多候选**：映射权限码支持 `a|b`，任一满足即放行（共 20 条）

### 2.2 数据层

| 表 | 职责 | 现状 |
|---|---|---|
| `t_admin_role` | 管理员 ↔ 角色 | 多对多 |
| `t_role` | 角色定义（6 内置：super_admin / order_manager / kitchen_manager / data_analyst / front_desk / operator） | ✅ |
| `t_role_permission` | 角色 ↔ 权限码 | 补丁式维护 |
| `t_permission` | 权限码注册表 | ✅ 聚合 22 码（11 个 migration） |
| `t_api_permission` | 接口 ↔ 权限码映射 | DB 聚合 326 条 |

### 2.3 数据范围（已实现三级，与连锁架构文档一致 ✅）

```
HQ（super_admin 角色） → 全店可见，豁免门店校验
REGION（t_admin_region → t_shop.region_id） → 解析为 shop_id 集合
SHOP（t_admin_shop 显式绑定） → 明确 shop_id 列表；空表 = 无范围
REGION ∩ SHOP 取交集（防区域放大权限）
```

### 2.4 通道隔离（✅ 正确）

- B 端：JWT（Authorization: Bearer）
- C 端：X-User-Token
- KDS：设备令牌（REST 独立鉴权）

## 3. 问题诊断

### 3.1 P0 · 数据不可复现（阻断级）

**P0-1 基础权限种子 SQL 缺失**
- `Role.java` 注释引用 `docs/db_diancan_permission.sql`，但**该文件在仓库中不存在**；
- 6 个内置角色、16 个基础权限码（admin:login/password/manage、order:view/operate/config、dish:manage、table:manage、banner:manage、statistics:view、user:view/points、kds:view/operate/config）及基础授权的种子数据**无法从仓库重建**；
- 影响：新环境/新库初始化后基础 RBAC 缺失，只能靠现网 DB 手工导出；权限体系"不可复现、不可审计"。

### 3.2 P1 · 一致性失控

**P1-1 接口映射双源、SSOT 分散**
- DB `t_api_permission` 326 条：靠 `init_api_permission.sql` + 20+ 个 `db_migration_*.sql` / `patch_*.sql` **人工增量维护**；
- 代码内置 `ApiPermissionMapping.java` 268 条：运行时兜底；
- 两处**无一致性校验**：同一路径可能两处权限码不同，以运行时顺序为准，漂移不可见。

**P1-2 文档与代码全面脱节**
- `docs/权限设计.md` §2.2 只列 **16 个权限码**；实际代码内置 26 码 + DB 注册 22 码（并集 38+），含未收录码：`cashier:operate`、`material:manage`、`daily:settle`、`shop:manage`、`payment:config:read/write`、`coupon:manage`、`access:view/manage`、`log:view/archive/export`、`marketing:firstorder:view/manage`、`notifications:view/manage`、`printing:view/manage`、`report:view/export`、`settings:view/manage`、`inventory:view/manage`、`table:operate`、`announcement:view`；
- 权限信息散落三份文档（权限设计.md / B端接口与权限码汇总.md / API.md），互相不同步。

**P1-3 新权限码补丁式授权、漏授即 403**
- 11+ 个 `db_migration_*.sql` 各自 INSERT 权限码 + 授权（`SELECT ... WHERE r.role_code IN (...) AND p.permission_code IN (...)` 模式），授权对象以 super_admin 为主；
- `AdminPermissionServiceImpl` **无 super_admin 代码级特判**（纯查表）→ 新增码若漏授，**超管也会 403**；
- 授权矩阵 SQL 层聚合不完整（部分脚本为 `role_code = 'x'` 单值写法、跨行 JOIN 组合），**完整矩阵需从现网 DB 导出确认**（见 §7 开放问题）。

**P1-4 新旧 RBAC 双轨**
- `/admin/rbac/*` 自 v1.2.132 起 @Deprecated（迁移至 `/admin/access/*` 乐观锁新版），但**旧接口全部仍在运行**，且 DB 映射保留旧路径；
- 双套接口 → 维护面翻倍、审计追踪两套、前端切换未完成。

### 3.3 P2 · 设计欠规范

- **P2-1 权限码命名不统一**：`payment:config:read`（三级前缀）、`daily:settle`（动作命名）、`cashier:operate`（角色语义）、`marketing:firstorder:view`（混合）——无统一词汇表；
- **P2-2 `|` 多候选 20 条未逐条审查**：任一权限即可操作（如 `dish:manage|cashier:operate` = 收银员可改菜），需确认是否放权过度；
- **P2-3 白名单硬编码 19 处**（AUTHENTICATED_ONLY 6 + SHOP_EXEMPT 13）：新增接口进入前缀即绕过校验/仅需登录，无配置化与变更审计；
- **P2-4 授权粒度**：部分接口（如 `/admin/coupon/*` 内置映射 `POST` 前缀）方法粒度粗糙，GET/POST 未拆分时权限码不区分读/写。

### 3.4 附：映射缺口复核记录（防误读）

早期自写脚本曾报"71 / 84 个疑似无映射端点"，经修复三个解析 bug 后复核为 **0 缺口**：

| 解析 bug | 影响 | 修复 |
|---|---|---|
| DB path 被 `rstrip('/')` | 破坏「尾斜杠 = 前缀通配」语义（如 /admin/administrator/） | 保留原样，匹配时区分前缀/精确 |
| 端点 method 首字母大写（`Get`）vs 映射 `GET` | 精确方法映射全不命中 | 统一 upper() |
| 未支持 DB 的 `*` 段通配（`/admin/access/roles/*`） | {id} 路径全报缺口 | 匹配逻辑增加 `*` 段通配 |

**结论：接口→权限映射层 361 端点全覆盖，无缺口。** 若后续重跑，用 `audit_permission_gap.py`（已修复）。

## 4. 目标态：专业权限设计系统

### 4.1 设计原则

| 原则 | 说明 |
|---|---|
| **单一事实源** | 接口映射、权限码、授权矩阵各只有一个权威来源，其余为派生/校验 |
| **先范围后能力** | 先判定数据范围（HQ/REGION/SHOP），再判定业务权限码；范围与能力 AND |
| **可复现** | 任何新环境可由脚本一键重建全部权限数据 |
| **可审计** | 白名单、授权、映射变更全部留痕（接入审计日志模块） |
| **失败关闭** | 映射缺失/权限表异常 → 拒绝，不静默放行 |
| **最小粒度** | 权限码按 `域:子域:动作` 命名，view/manage 成对，杜绝 `|` 意外放大 |

### 4.2 四层模型

```
身份（t_admin）→ 角色（t_role）→ 权限码（t_permission）→ 资源（接口/操作/数据范围）
```

- 角色是**分配单元**（解决"给谁"），权限码是**能力单元**（解决"能做什么"），接口映射是**资源绑定**（解决"做什么需要什么"）；
- 数据范围独立于权限码：同一权限码（如 order:view）+ 不同范围（HQ/SHOP）= 不同可见数据。

### 4.3 权限码体系

**命名规范**：`<域>:<子域>:<动作>`；动作枚举固定：`view`（只读）/ `manage`（写）/ `operate`（业务动作）/ `config`（配置）/ `export`（导出）/ `settle`（结算）/ `assign`（分配）。

**成对原则**：每个资源域至少注册 `view` + `manage` 一对（如 `order:view` + `order:manage`）。

**域目录**（建议定稿，存量码做别名映射表）：

| 域 | 动作 | 说明 |
|---|---|---|
| admin | login / password / manage | 账号与管理员管理 |
| order | view / operate / config | 订单 |
| dish | view / manage | 菜品/分类/单位 |
| table | view / operate / manage | 桌台 |
| kds | view / operate / config | 厨显 |
| user | view / points | 会员 |
| statistics | view | 报表分析 |
| report | view / export | 报表导出 |
| marketing | view / manage（firstorder 子域） | 营销 |
| coupon | view / manage | 优惠券 |
| inventory | view / manage | 库存 |
| payment | view / manage / config | 支付渠道 |
| printing | view / manage | 打印 |
| notification | view / manage | 通知 |
| log | view / archive / export | 日志审计 |
| settings | view / manage | 系统设置 |
| access | view / manage | 权限管理本身 |
| material | view / manage | 物料 |
| banner / announcement / shop / daily | 按需 | 其余存量域 |

**注册表机制**：`t_permission` 为唯一码表；**启动自检**校验代码/DB 映射引用的每个权限码 ∈ 注册表，未注册 → 告警（防拼写漂移）。

### 4.4 角色体系

- 保留 6 内置角色（存量兼容），开放自定义角色（新版 `/admin/access/*` 已支持）；
- **角色-权限矩阵**以 `t_role_permission` 为唯一来源，管理页可视化维护（新版 access 已具备基础）；
- **super_admin 双保险**（待定，见 §7）：现状纯查表、无特判；建议 `isSuperAdmin` 短路返回全权限 OR 矩阵为空时启动告警，二选一需产品确认语义（现有文档明确"只有显式绑定 super_admin 角色并通过角色权限表配置才能获得总部权限"）。

### 4.5 接口映射单一事实源

- **权威**：`t_api_permission`（DB）；
- **代码内置** `ApiPermissionMapping.java` 降级为：启动自检基准 + 极端兜底（DB 不可用时）；
- **启动自检**（应用启动时执行）：
  1. 全量扫描 Controller 端点 → 与 DB 映射比对；
  2. 缺失映射 / 多余映射（孤儿）/ 权限码未注册 → WARN 日志（可选升级为失败关闭开关）；
- **路径匹配约定唯一化**：尾斜杠=前缀通配、`*`=段通配、精确路径——写入代码注释与文档，禁止新增第三种风格。

### 4.6 数据范围模型（现状已实现，维持）

HQ / REGION / SHOP 三级 + REGION∩SHOP 交集，与 `docs/admin_chain_permission_architecture.md` §2 一致，**无需改造**，仅需把「登录/me 返回 scope + shops」契约（架构文档 §3.3）补到 OpenAPI。

### 4.7 治理机制

| 机制 | 内容 |
|---|---|
| 种子可复现 | 补齐 `db_diancan_permission.sql`（现网 DB 导出基础 16 码 + 6 角色 + 授权），纳入 docs |
| 模块迁移模板化 | 新模块 = 1 个 migration 脚本（注册码 + 映射 + 授权 + 文档引用），禁止散落多个 patch |
| 文档单一化 | 合并权限设计.md / B端接口与权限码汇总.md / API.md 权限部分 → 一份《权限参考》，由脚本生成 |
| 白名单配置化 | AUTHENTICATED_ONLY / SHOP_EXEMPT 迁至配置表（t_security_config），变更留审计 |
| 双轨收敛 | 下线 /admin/rbac/*（前端切 /admin/access/* 后删接口 + 删映射） |
| 审计接入 | 权限拒绝事件（auditDenied）、授权变更、白名单变更全部写审计日志 |
